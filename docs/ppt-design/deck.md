## 03 · 痛点


- **版式**：content（三卡）
- **配图**：无（纯文字卡片）
- **标题**：AI 十秒给你一份行程，但你不敢照着走
- **正文**（三张卡）：
  1. **不可验证**：它说“这家店不错”，没有来源、没有抓取时间
  2. **不可重规划**：下雨了、太累了，只能整份重来
  3. **不可解释**：为什么选它、为什么改它，全是黑盒
- **口播**（50s）：我们访谈里最常见的一句话是“看着挺合理，但我不会真的按它走”。这三件事一起出现，问题就不在生成速度，而在信任。

## 04 · 解法闭环


- **版式**：content（矢量图，珊瑚路径）
- **配图**：无（Plan → Verify → Replan → Explain 闭环图）
- **标题**：把“生成”升级成一条可验证的决策链
- **正文**：
  - 每条行程可验证
  - 每个推荐有证据
  - 每个变化可追溯
  - 每次重规划可回滚
- **口播**（60s）：四个环节组成闭环。Plan 负责把候选做扎实；Verify 用硬规则和证据卡把关；不通过就进入 Replan，生成替代方案；Explain 让每一个数字都能追到来源。

## 05 · 数据流

- **版式**：content（五段横向管线，原生形状）
- **配图**：无（矢量）
- **标题**：数据从哪来，到哪去
- **正文**：
  - 实时数据源：高德 POI / 路线 / 天气，每条都带抓取时间
  - 候选池：多类别检索、去重、聚类，每天至少一顿正餐
  - 规则引擎：天级 7 条 + 行程级 5 条，输出评分与问题清单
  - 证据卡：来源 / 真实或估算 / 置信度 / 一句话理由
  - 行程版本：提案、确认、撤销，版本号可回溯
  - 底注：任何一级缺失 → 明确降级并标注，不编造数字
- **口播**（45s）：这条链路是本项目的骨架：高德和天气数据进入候选池，规则引擎先判能不能过，证据卡记录每个判断的来源，最后才写成一份可回滚的行程版本。任何一级拿不到数据，系统都会降级并标注，而不是补一个看起来合理的数字。

## 06 · Plan


- **版式**：content（左文右图 4:8）
- **配图**（裁掉底部“还缺信息”提示）：

  ![对话式规划](../../shots/deck/assets/02-planning.png)

- **标题**：先把候选做扎实，再交给模型排程
- **正文**：
  - 多类别检索：景点 / 餐饮 / 咖啡 / 活动
  - 去重 + 地理重排，每天至少一顿正餐
  - LLM 只做排序与叙事，不负责事实
- **口播**（50s）：纯 LLM 排程最大的问题是候选不够。我们先把候选扩到多类别、去重、按地理聚类，再让模型在候选里做选择。模型不发明地点，也不发明营业时间。

## 07 · Verify


- **版式**：archive，象牙白 `#F5F1E8`
- **配图**：

  ![校验面板](../../shots/deck/assets/04-verify.png)

- **标题**：12 条硬规则，拦下不该通过的行程
- **正文**：
  - 天级 7 条：地点太少、重复地点、到达时已闭馆、缺正餐、安排过密、天气风险、无障碍风险
  - 行程级 5 条：跨天重复、相邻交通过长、超预算、超步行上限、地点未核实
  - 输出一份可读的校验报告：分数 + 问题 + 建议
- **口播**（60s）：这 12 条都是确定性规则，不依赖模型判断。截图里这份行程 70 分，没有硬性冲突，但有 3 个“安排过密”的提醒。分数不是重点，重点是每一条提醒都能指到具体地点和具体时间。

## 08 · Replan


- **版式**：archive，象牙白
- **配图**：

  ![一键修复](../../shots/deck/assets/05-replan.png)

- **标题**：变化是提案，不是命令
- **正文**：
  - 触发：闭馆、下雨、太累、超预算、晚点
  - 系统给出替代方案 + 量化 Diff + 改动原因
  - 用户确认后才写入；令牌一次性、10 分钟有效、只存哈希
- **口播**（60s）：很多人做重规划是直接改掉用户的行程。我们不这么做。任何变化都先变成一份提案，带前后对比和原因；用户点确认才落库。令牌十秒内只能用一次，十分钟过期，服务端只保存哈希。

## 09 · Explain


- **版式**：archive，象牙白
- **配图**（裁切至“高德来源 90% 置信 · 查看依据”）：

  ![证据卡局部](../../shots/deck/assets/05-replan.png)

- **标题**：为什么选它、为什么改它，都能点到来源
- **正文**：
  - 证据卡：来源 / 抓取时间 / 真实或估算 / 置信度 / 一句话理由
  - 估算值永远带标注，不伪装成真实数据
  - 改动可回滚，版本可对比
- **口播**（50s）：这张卡是整套系统的核心。地点从哪来、什么时候抓的、是真实数据还是估算、置信度多少、为什么选它，全部写清楚。用户不需要相信我们，只需要相信来源。

## 10 · 差异化

- **版式**：content（三列对比表）
- **配图**：无
- **标题**：同样的模型，差别在模型之外
- **正文**：
  - 事实来源：模型记忆 / 高德 POI、路线、天气，带抓取时间
  - 验证：人工目测 / 12 条确定性规则，天级 + 行程级
  - 重规划：整份重生成 / 提案 + 量化 Diff + 改动原因
  - 回滚：没有版本 / 版本可对比，一键撤销
  - 入口：一个网页 / Web、CLI、MCP 共用同一命令层
  - 说明：对比的是“把需求直接丢给通用模型”这一种用法，不针对具体产品
- **口播**（40s）：通用模型也能写出像样的行程，差别在于它无法证明自己是对的。我们把数据来源、验证规则、重规划提案、回滚和入口全部做成可核对的机制，这部分不在模型里，在系统里。
